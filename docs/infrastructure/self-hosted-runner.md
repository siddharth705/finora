# Self-hosted GitHub Actions runner

CI for this repository does not run on GitHub-hosted runners. It runs on one self-hosted machine.
This document is what you need to operate, diagnose, or rebuild that setup; it exists because the
knowledge otherwise lives in one person's shell history.

## Why self-hosted

GitHub-hosted runners stopped starting entirely on 2026-08-07:

> The job was not started because recent account payments have failed or your spending limit needs
> to be increased.

That is an account-level block, not a workflow problem, and no change to `.github/workflows/ci.yml`
could work around it. Every push and pull request went unverified until the migration. Resolving the
billing block was considered and deliberately declined, so this is the permanent arrangement rather
than a stopgap.

## The runner

| | |
|---|---|
| Name | `finora-m5` |
| Runner ID | 21 |
| Labels | `self-hosted`, `macOS`, `ARM64` |
| OS | macOS on Apple Silicon |
| Install path | `~/actions-runner` |
| Runner package | `actions-runner-osx-arm64-2.336.0` |
| Registered to | the `siddharth705/finora` repository (not an org) |

`.github/workflows/ci.yml` targets it with `runs-on: [self-hosted, macOS, ARM64]` on all five jobs.

The label list is specific rather than a bare `self-hosted` on purpose: `self-hosted` alone matches
ANY self-hosted runner, so a second machine joining later on a different OS or architecture could
silently claim these jobs and fail in ways that look like product breakage.

## Operating it

```bash
cd ~/actions-runner

./svc.sh status      # is the service running?
./svc.sh start
./svc.sh stop
./svc.sh install     # register as a launchd agent, so it survives reboot and logout
./svc.sh uninstall
```

`svc.sh` is generated by `config.sh` during registration, so it only exists once the runner has been
configured.

Run it as a service (`svc.sh`), not with `./run.sh`. A foreground listener started from a terminal
looks identical from GitHub's side right up until that terminal closes, the user logs out, or the
machine reboots — and the failure mode is jobs queueing forever rather than failing, which reads as
"CI is slow" instead of "CI is down".

## Health check

Run this after a reboot, a macOS update, or any time CI looks stuck. Work down the list: each step
assumes the ones above it passed, and the first failure is usually the whole answer.

```bash
# 1. Is the runner registered and idle?  Expect: online, busy=false
gh api repos/siddharth705/finora/actions/runners \
  --jq '.runners[] | "\(.name) \(.status) busy=\(.busy) labels=[\([.labels[]|.name]|join(","))]"'

# 2. Is the service running locally?
cd ~/actions-runner && ./svc.sh status

# 3. Is Docker up?  Expect: a version, then a container table (possibly empty)
docker version --format '{{.Server.Version}}' && docker ps

# 4. Is anything holding a port CI needs?  Expect: no output
lsof -nP -iTCP:8081 -sTCP:LISTEN; lsof -nP -iTCP:5433 -sTCP:LISTEN

# 5. Does a real job get picked up?
gh workflow run ci.yml --repo siddharth705/finora --ref main
gh run list --repo siddharth705/finora --limit 1
```

Reading the results:

- **Runner absent from step 1** — it never registered, or the registration was removed. Re-register
  (see "Recovering on a new machine").
- **Runner `offline`** — the machine is asleep, the service is not running, or there is no network.
  Step 2 distinguishes them.
- **`busy=true` for a long time** — either a job is genuinely wedged, or the queue is deep. One
  runner drains one job at a time; see "Throughput".
- **Step 3 fails** — Docker Desktop is not running. This is the single most likely cause of a red
  build after a reboot, and it fails the `backend` and `smoke` jobs at container startup rather than
  on an assertion, so the error does not look like a Docker problem at first glance.
- **Step 4 finds a listener** — a previous run left the backend (port 8081) or Postgres (5433)
  behind. The `smoke` job's teardown step handles this normally; a killed run can skip it. Clear
  with `docker rm -f finora-ci-postgres` and `pkill -f finora-backend`.
- **Step 5 queues but never starts** — the labels in `runs-on` do not match the labels the runner
  registered with. This is the failure that looks like nothing is wrong: GitHub reports the job as
  pending indefinitely rather than failing it.

## Host requirements

These are things a GitHub-hosted `ubuntu-latest` image provided for free. Nothing installs them for
you here.

**Docker Desktop, running.** Two jobs need it: `backend` (Testcontainers starts Postgres for the
integration tests) and `smoke` (Postgres container). It is a desktop app rather than a daemon, so a
reboot, a logout, or a machine that slept leaves it down. Enable **Docker Desktop → Settings →
General → Start Docker Desktop when you log in**.

**python3.** Thirteen guard-script steps across four jobs, and six more in `.husky/pre-commit`. Note
those call `python3` and never `python`: macOS removed the bare `python` command in 12.3 and Ubuntu
has not shipped it since 20.04. In the hook the consequence is worse than a failed job — each call
is `|| exit 1`, so a missing `python` blocks every commit. Do not "simplify" the spelling back.

**The machine must be awake.** macOS sleeps the system shortly after the display sleeps by default,
and a sleeping runner takes queued jobs with it. The conservative setting for a machine that is also
somebody's laptop is to prevent sleep **on power adapter only**, leaving battery behaviour alone:
System Settings → Displays → Advanced → "Prevent automatic sleeping on power adapter when the
display is off", equivalently `sudo pmset -c sleep 0`.

Java and Node are deliberately NOT requirements: `actions/setup-java` and `actions/setup-node`
install them per job exactly as on a hosted runner, and Temurin publishes ARM64 macOS builds.

## Throughput

One runner executes **one job at a time**. The five jobs in `ci.yml` therefore serialise rather than
running in parallel, and a full run's wall-clock is roughly the sum of the jobs rather than the
slowest one. Measured on `finora-m5`, cold caches then warm:

| Job | Cold | Warm |
|---|---|---|
| Backend | 2m56s | ~2m20s |
| End-to-end smoke | 5m15s | ~2m20s |
| Mobile | 2m40s | ~1m35s |
| User frontend | 1m23s | ~2m |
| Admin portal | 1m12s | ~1m |

Warm is the normal case: unlike a hosted VM, this machine keeps `~/.m2`, `node_modules` and the
Playwright browsers between runs.

This is fine for a small team and becomes the bottleneck when several PRs land at once. Two ways
out, in order of effort:

1. Keep `on: push` narrow — it is `branches: [main]` for exactly this reason. See the comment at the
   top of `ci.yml`.
2. Register a second runner. Additional runners can live on the same machine in their own
   directories with their own names; nothing in the workflow has to change.

## Security

A self-hosted runner executes workflow code from every pull request on this machine, under your user
account, with access to everything that account can reach — the home directory, `~/.m2`, SSH keys,
the login keychain. That includes dependabot pull requests, which run `npm install` and its install
scripts.

For a private repository with a single trusted committer that is a reasonable trade. It stops being
one the moment this repository takes pull requests from outside contributors, or goes public.
Revisit it then rather than discovering it then.

## Recovering on a new machine

1. Install Docker Desktop and set it to start at login.
2. Download the runner package from the repository's Settings → Actions → Runners → New self-hosted
   runner page. That page generates a registration token; use the commands it shows rather than
   copying them from here, since they change between runner versions and the token is short-lived.
3. Run `./config.sh` with that token. Give the runner a name, and make sure its labels match
   `runs-on` in `ci.yml`.
4. `./svc.sh install && ./svc.sh start`.
5. Work through the health check above. Step 5 is the one that proves it end to end.
6. If the machine's OS or architecture differs from this one, update `runs-on` in
   `.github/workflows/ci.yml` to match, and revisit the two macOS-specific choices in that file: the
   hand-rolled Postgres container in `smoke` (a Linux runner can use a `services:` block instead)
   and `playwright install` (a Linux runner wants `--with-deps` back).

## Going back to GitHub-hosted runners

If the billing block is ever resolved and hosted runners are wanted again, the change is the five
`runs-on` values plus restoring the `services:` block in the `smoke` job. Keep the `python3`
spelling, the teardown step, and the narrowed `push` trigger either way — all three are correct on
hosted runners too.
