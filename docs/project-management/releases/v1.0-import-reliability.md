# Finora v1.0 — Import Reliability

**Tagged** `v1.0-import-reliability` at `75662b0` on 2026-08-07.

The rule this milestone enforces, throughout: **the system proposes, the user decides, and nothing
happens to a person's ledger that they did not choose.**

---

## What this milestone delivered

Scoped as Deliverable 0 and WI1–WI7, plus WI5A which the validation gate added.

**Merchant learning became an independent subsystem.** An import no longer blocks on learning, and a
learning failure no longer costs an import. This is the defect the milestone existed to close: one
lost race against `UNIQUE(user_id, merchant_id, category_id)` used to roll back every transaction in
a statement the user had already reviewed and approved. Confirmations are now queued to a durable
table and applied after commit by a worker that claims with `FOR UPDATE SKIP LOCKED`, backs off
exponentially, and recovers rows abandoned by a process that died mid-apply. *(Deliverable 0, WI1 —
V62)*

**Merchant Learning Queue** — the operator screen that makes the above safe to have. Something that
fails quietly in the background has to be visible to somebody. Every row carries the statement, the
import session and the affected user, so a failure is diagnosable rather than merely visible, and
the screen leads with the fact that nothing in it ever blocked an import. Retry per row or in bulk.
*(WI2 — V63)*

**Staging writes nothing.** Previewing a statement creates no merchant, no alias, no learning row,
no transaction. Asserted by counting rows before and after rather than by verifying a mock went
uncalled — the mocked version of that test passed for as long as it existed while the real code
wrote merchants during preview. *(WI3)*

**Temporary merchants and the Merchant Review Center.** WI3 needed somewhere for an unrecognised
merchant to go, and `TEMPORARY` is it: a guess the engine will make but not present as fact.
Operators approve, rename, or merge — merging repoints transactions, aliases and learning history
rather than deleting them. Discarding a merchant that has transactions attributed to it is refused
outright, with the reason stated where the action would have been rather than as an error
afterwards. *(WI4 — V64)*

**Duplicate Transaction Review.** Detection stopped being a filter. A flagged row used to be
silently unticked, which was wrong in both directions — a genuine re-import got skipped without
anyone confirming it, and two identical coffees bought on the same day got skipped too. Now the row
arrives with the transaction it appears to repeat, and Confirm Import stays disabled until every
flagged row has an explicit answer. *(WI5)*

**And the decision survives what runs after it.** The validation gate caught reconciliation
re-marking rows the user had explicitly confirmed, which stripped them from every spend calculation:
the ledger held ₹1,618.50 while the dashboard reported ₹1,528.50, the difference being exactly the
transactions the user had asked for. The answer now travels with the row and reconciliation honours
it — permanently, not just on the run following the import. *(WI5A — V65)*

**Password and session policy** were resolved by product decision and needed no code. *(WI6, WI7)*

## Testing infrastructure added

- **End-to-end suite** — 103 specs driving both portals in a real browser against a real backend and
  a real database. Every spec asserts a business outcome rather than a rendering: not "did the screen
  show something" but "did the user's decision survive the whole system".

## Defects this milestone's own validation found and fixed

1. **Reconciliation overruled a user's explicit duplicate decision**, removing confirmed
   transactions from every spend total. Found by driving the real UI against a real database — it
   existed nowhere else.
2. **A corrupted PDF returned `INTERNAL_ERROR`** carrying a raw PDFBox message. A 500 for a problem
   the server did not have, plus a library internal handed to someone who cannot act on it. Now a
   422 telling them to download the file again.
3. **Rate limits were hardcoded**, leaving the product impossible to test end to end at any useful
   volume — and giving operations no remedy short of a redeploy for a customer behind a NAT.

Two more were found by the end-to-end suite's own first isolated run: an out-of-sync
`package-lock.json` that would have broken CI's install step, and a relative navigation that pointed
the operator assertions at the marketing site.

## Known operational note

Two Maven builds sharing one `backend/target/` will delete and rewrite each other's class files
mid-run. Locally that presents as an intermittently red build with a different failing set each time
— ArchUnit scans returning empty, `NoClassDefFoundError` for classes that plainly exist — and it all
passes in isolation, which is the tell. CI is unaffected; it gets its own checkout.
