# Repository structure audit — deferred items

Structural audit of `main` at `3173d93`, 2026-08-05, after a stretch of parallel work across four
audit branches and two mobile feature branches. Scope was deliberately narrow: where files live and
whether each feature stayed inside its own area. Not a code or bug review.

## What was checked and found clean

- **Module containment.** No `.java` outside `backend/`, no `react-native` imports in
  `frontend`/`admin-portal`, no `react-dom`/`vite` imports in `mobile/src`.
- **Cross-module imports.** No source file in any app imports from another app's `src/`, and no
  relative import escapes its own module.
- **Per-module config.** `frontend`, `admin-portal` and `mobile` each carry their own complete
  `package.json` / `tsconfig.json` / `eslint.config.js` plus the right bundler config
  (`vite.config.ts` for the two web apps, `app.config.ts` for Expo). Nothing borrowed or shared.
- **Root-level config** is all genuinely repo-wide: `commitlint.config.js`, `docker-compose.yml`,
  and the root `package.json`/`package-lock.json` that exist only to install husky and commitlint.
- **Merge and cherry-pick leftovers.** No conflict markers, no `.orig`/`.rej`/`.bak`/`~` files.
- **Temp, debug and build output.** No `node_modules/`, `target/`, `dist/`, or `coverage/` tracked;
  no editor or OS junk (`.DS_Store`, `Thumbs.db`, `.swp`).

## Fixed in this pass

Two orphaned session-handoff artifacts were removed. Both were transient delivery notes from an
earlier zip-based workflow rather than repository documentation, both were stale since 2026-08-01,
and neither was referenced by README, CONTRIBUTING, `docs/`, or CI:

- `MANIFEST.md` — a file-bundle listing that opened "Generated by diffing the current working state
  against the exact original zip you uploaded" and instructed the reader to "Unzip directly over
  your repo root". Describes a 63-file bundle that has long since landed.
- `CHANGES.md` — a per-bundle changelog ("what's new since the Brandfetch fix bundle"), closing with
  a note that its author could not compile the Java changes and asking the reader to run the tests.
  Duplicated `CHANGELOG.md`'s role while describing one delivery rather than the project.

Both remain in git history if the narrative is ever wanted.

## Deferred — needs an owner decision, not a structural fix

### 1. `CHANGELOG.md` has not been touched since the initial commit

It is a well-formed Keep a Changelog file, last modified in `cb6ba7b` (2026-07-31), while the
project has moved through 49 CI runs and several feature merges since. Either it is meant to be
updated per release and has silently lapsed, or the project tracks changes solely through commit
history and the file is vestigial.

Not fixed here because both answers are defensible and the choice is a process decision. Worth
settling explicitly: a changelog that is 5 days stale is worse than none, because a reader trusts it.

### 2. `docs/` root holds 11 loose files alongside two organised subdirectories

`docs/architecture/` and `docs/engineering/` exist and are used, but eleven documents sit directly
at `docs/`. They are not one kind of thing:

- **Specs / EDS** — `financial-evidence-engine-eds.md`, `financial-intelligence-engine-spec.md`,
  `rule-engine-relationship-engine-eds.md`, `statement-intelligence-engine-spec.md`
- **Philosophy / direction** — `finora-financial-intelligence-philosophy.md`,
  `engineering-directive-phase1.md`
- **Implementation notes** — `iam-priority2-implementation-notes.md`,
  `bootstrap-setup-future-work.md`
- **Transient team comms** — `team-message-financial-intelligence-kickoff.md`,
  `team-message-financial-intelligence-v1-closeout.md`,
  `team-message-financial-intelligence-workspace-kickoff.md`

The three `team-message-*` files in particular read as point-in-time announcements rather than
reference documentation, which is the same shape as the two artifacts removed above — but unlike
those, they may be deliberately retained as a project record.

Not fixed here because moving documentation breaks inbound links from commit messages, ADRs and
external references, and choosing the taxonomy (by lifecycle? by subsystem?) is an owner call, not
a structural one. A `docs/specs/` and `docs/decisions/` split is the obvious candidate if a sweep
is wanted.
